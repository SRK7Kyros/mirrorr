## CRITICAL

### C1. `useBulkDelete` hardcodes `/sessions/` endpoint — all non-session bulk deletes are broken

**File:** `src/hooks/use-bulk-delete.ts` · **Lines:** 23
**Severity:** CRITICAL

The `_deleteFn` parameter is accepted but **never used** (prefixed `_` to silence lint). The hook hardcodes:

```ts
apiRequest(`/sessions/${id}`, { method: "DELETE" })
```

This means **bulk delete for Recordings, Profiles, and Autoruns all hit the wrong endpoint** (`/sessions/{id}`), silently failing or deleting sessions instead.

**Impact:** Bulk delete on the Recordings, Profiles, and Autoruns pages sends DELETE requests to `/sessions/{id}` instead of `/recordings/{id}`, `/profiles/{id}`, or `/autoruns/{id}`. These either 404 or (worse) delete unrelated sessions.

**Fix:** Use `_deleteFn` instead of the hardcoded path:

```ts
mutationFn: async (ids: number[]) => {
    const results = await Promise.allSettled(
        ids.map((id) => _deleteFn(id)),
    );
    // ...
}
```

## HIGH

### H1. Missing query cache invalidation after session create

**File:** `src/routes/_app/sessions/index.tsx` · **Lines:** 526–529
**Severity:** HIGH

The `CreateSessionPanel` create mutation has no `invalidateQueries` call:

```ts
const createMutation = useMutation({
    mutationFn: (data: Record<string, unknown>) => sessionsApi.create(data as any),
    onSuccess: () => {
        onClose();
        toast.success("Session created");
        // ← Missing: queryClient.invalidateQueries({ queryKey: ["sessions"] })
    },
});
```

After creating a session, the sidebar list won't update until the next WS event or page refresh (up to 30s staleTime). The autoruns create mutation correctly invalidates its query key.

**Fix:** Add `queryClient.invalidateQueries({ queryKey: ["sessions"] })` to `onSuccess`.

### H2. Missing query cache invalidation after recording delete

**File:** `src/routes/_app/recordings/index.tsx` · **Lines:** 37–40
**Severity:** HIGH

```ts
const deleteMutation = useMutation({
    mutationFn: (id: number) => recordingsApi.delete(id),
    onSuccess: () => {
        toast.success("Recording deleted");
        // ← Missing: queryClient.invalidateQueries({ queryKey: ["recordings"] })
    },
});
```

Unlike profile and autorun pages, recordings has no `queryClient` import or invalidation. Deleted recordings remain in the sidebar until refresh.

**Fix:** Import `useQueryClient` and add invalidation.

### H3. `as any` type bypass in session and autorun create mutations

**Files:** `src/routes/_app/sessions/index.tsx:525`, `src/routes/_app/autoruns/index.tsx:385`
**Severity:** HIGH

```ts
sessionsApi.create(data as any)   // sessions/index.tsx
autorunsApi.create(data as any)   // autoruns/index.tsx
```

These `as any` casts bypass all type checking on the request body. If the API contract changes (field renamed, type changed), TypeScript won't catch it. The `sessionsApi.create` and `autorunsApi.create` functions already have typed parameter signatures — the `data` object should be constructed to match.

**Fix:** Remove the `as any` by constructing properly typed objects, or use `Omit<SessionCreateBody, 'profile_id'>` types directly.

## MEDIUM

### M1. `InlineDeleteButton` in recordings receives `deleteMutation: any`

**File:** `src/routes/_app/recordings/index.tsx` · **Lines:** 127–131
**Severity:** MEDIUM

```ts
function InlineDeleteButton({
    deleteMutation,   // ← typed as `any`
    ...
}: {
    id: number;
    deleteMutation: any;  // ← no type safety
    ...
})
```

The `InlineDeleteButton` component in recordings is locally defined (not the shared one from `@/components/inline-delete-button`), and types `deleteMutation` as `any`. This defeats TypeScript checking on `deleteMutation.isPending` and `deleteMutation.variables`.

**Fix:** Import and reuse `InlineDeleteButton` from `@/components/inline-delete-button`, or properly type the mutation.

### M2. `_unused_id` parameter in shared `InlineDeleteButton`

**File:** `src/components/inline-delete-button.tsx` · **Line:** 22
**Severity:** MEDIUM

```ts
export function InlineDeleteButton({
    id: _unused_id,   // ← id is accepted but never used
    ...
})
```

The `id` prop is accepted in the interface but immediately discarded. The component relies on the `onClick` callback to handle deletion. If a consumer passes `id` expecting it to be used internally, they'd be confused.

**Fix:** Either remove `id` from the interface entirely, or document that it's a pass-through identifier for external use only.

### M3. Duplicate `InlineDeleteButton` — recordings defines its own

**Files:** `src/routes/_app/recordings/index.tsx:125–158`, `src/components/inline-delete-button.tsx`
**Severity:** MEDIUM

Recordings defines a local `InlineDeleteButton` with different behavior (it reads `deleteMutation.isPending` and `deleteMutation.variables` directly) while profiles uses the shared component from `@/components/inline-delete-button`. This is a classic pattern duplication.

**Fix:** Unify to use the shared `InlineDeleteButton` component, adapting it as needed.

### M4. Auth-related query keys (`["auth-me"]`, `["admin-users"]`) not invalidated on auth state changes

**File:** `src/routes/_app/profile.tsx` · **Lines:** 159–166
**Severity:** MEDIUM

The profile page fetches `authApi.me()` with key `["auth-me"]` and `authApi.users()` with `["admin-users"]`. When a user changes their password or an admin deletes a user, the `["auth-me"]` query is never invalidated, so the displayed user info can be stale.

**Fix:** After password change success, add `queryClient.invalidateQueries({ queryKey: ["auth-me"] })`.

### M5. No delete confirmation dialog — all destructive actions fire immediately

**Files:** `src/routes/_app/sessions/index.tsx`, `autoruns/index.tsx`, `recordings/index.tsx`, `profiles/index.tsx`, `profile.tsx`
**Severity:** MEDIUM

Every delete action (single and bulk) fires immediately without confirmation. The `AlertDialog` component exists in the UI library but is never used for deletions. A misclick or accidental Enter/Backspace (which are bound as delete shortcuts) will permanently delete resources.

**Fix:** Wrap destructive actions in `AlertDialog` confirmation before executing.

### M6. Monitoring telemetry page accesses non-existent `session.duration_seconds` field

**File:** `src/routes/_app/monitoring/$sessionId.tsx` · **Lines:** 81–84
**Severity:** MEDIUM

```tsx
{sessionData.duration_seconds != null &&
    (sessionData.duration_seconds as number) > 0 && (
        <span>Duration: {formatDuration(sessionData.duration_seconds as number)}</span>
    )}
```

The `Session` Zod schema has no `duration_seconds` field. This is cast via `as Record<string, unknown>`, so it compiles but will always be `undefined`, making the duration display permanently hidden on the monitoring session detail page.

**Fix:** Compute duration from `started_at` / `ended_at` using the existing `getSessionTiming` helper (from sessions page) or remove the dead code.

## Positive Observations

The codebase is well-structured overall:

1. **Security posture is strong** — JWT tokens are in httpOnly cookies, `credentials: "include"` on all fetch calls, no tokens in localStorage, WS auth via cookies.
2. **Shared hooks eliminate duplication** — `usePluginConfig`, `useBulkDelete`, `useBulkExport`, `useSaveAsProfile`, `useMultiSelect`, `useWsConnection` are well-designed.
3. **Zod schemas are comprehensive** — All entity types have Zod schemas with types derived from them (no manual type duplication).
4. **WS → Query cache sync is excellent** — `use-ws-events.ts` patches the TanStack Query cache with zero-roundtrip entity data.
5. **Layout constants are centralized** — `lib/layouts.ts` prevents magic numbers from scattering.
6. **Consistent shadcn/ui adoption** — UI primitives are used consistently (minimal raw HTML for standard controls).
7. **No XSS vectors** — No `dangerouslySetInnerHTML` with user data, no `eval`, no `innerHTML`.
8. **Clean static analysis** — No console.log in production code, no `@ts-ignore`.
